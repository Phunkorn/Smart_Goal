3. Collaboration Architecture

Near real-time Adaptive Polling ไม่ใช่ WebSocket Real-time ใช้ HTTP requests สั้นตามรูปแบบ hosting เดิม ไม่ต้องอาศัย Redis, SSE หรือ persistent worker สภาพแวดล้อม DirectAdmin จริงเข้าตรวจไม่ได้ จึงเลือกวิธีที่ไม่ต้องพึ่งความสามารถเหล่านั้น

Initial Blade snapshot + version
  → local scene / pending draft
  → object batch + base_version + request_id
  → board lock + revision CAS + transaction
  → authoritative snapshot acknowledgement

Visible tab → GET document?since=revision
  unchanged → {ok:true, version:N, unchanged:true} (40 bytes ที่ทดสอบ)
  changed → delta {upserts, deleted, order}
  history pruned → coherent snapshot
  → three-way merge + stable IDs → existing keyed SVG/HTML renderer

Active 3s หลัง response, idleเกิน30sลดเป็น10s, hiddenหยุด board polling, กลับ tab/online sync ทันที; temporary read failure backoffถึง60s เฉพาะหน้ากระดาน Read-only clients รับ remote updates เช่นเดียวกัน ไม่มี polling ที่เพิ่มใน global layout

ยังมี global notification polling ของระบบเดิมแยกต่างหาก ไม่ใช้เป็นหลักฐานว่า Canvas เป็น realtime. Sources: resources/js/pages/workspace/autosave.js, resources/js/pages/workspace/synchronization.js, app/Services/WorkspaceBoardDocumentService.php

13. Deployment Instructions — ยังไม่ได้ดำเนินการ

  1. สำรองMySQLและprivateattachments; ทดลองด้วยสำเนาข้อมูลบนstagingก่อน ตรวจPHPversion/DBengine/permissionsและsessiondriverเดิม
  2. แจ้งให้ปิดแท็บกระดานก่อนdeployและเปิดmaintenancewindow ป้องกันmixed-versionclients โดยเฉพาะundo/attachmentquota semanticsใหม่
  3. ใช้migrationใหม่เพียงรายการนี้หลังตรวจpendingmigrationsอื่น หรือใช้SQL deploy/2026-11-25-workspace-collaboration.sql ตามconventionถ้าไม่มีArtisan ห้ามrunSQLซ้ำควบกับmigrationโดยไม่ตรวจmigrationsledger ไม่runmigrationเก่าแก้schemaย้อนหลัง
  4. Buildassetด้วยnpm run buildในขั้นเตรียมrelease และdeployPHP/Blade/manifest+hashedassetsชุดเดียวกัน; php artisan optimize:clearตามขั้นตอนโฮสต์ ไม่มีdependencyเพิ่ม
  5. เปิดstagingสองบัญชี ทดสอบsave/sync/offline/undo/upload/departmentisolation แล้วดูPHP-FPMslowlog,CPU/memory/workerqueueและMySQLlockingก่อนเปิดใช้งานจริง
  6. ตรวจphp artisan workspace:prune-attachments --dry-runบนstaging จากนั้นตั้งdailycronเรียกคำสั่งcleanupตามoperationalpolicyเดิม ไม่จำเป็นต่อความถูกต้องของsave/quotaและไม่มีpersistentworker
  7. ให้ผู้ใช้เปิดหน้าใหม่เพื่อโหลดassetล่าสุด รักษาHTTPSและprotectedmediapolicies ไม่เพิ่มpublic/privatepathcachebypass

ไม่ได้runmigration/SQLกับฐานข้อมูลport8001หรือProduction จึงยังต้องติดตั้งschemaก่อนเปิดใช้โค้ดSaveใหม่ที่นั่น; การทดสอบที่ยืนยันผลใช้port8012แยกเท่านั้น

14. Rollback Instructions

หยุดการแก้ไข/ปิดแท็บก่อนrollback, backupข้อมูลและpendingdraftที่จำเป็น, deployPHP/Blade/assetsรุ่นเดิมที่สอดคล้องกัน โดยคงschemaadditiveใหม่ไว้ snapshotในworkspace_board_documentsยังอ่านได้โดยcodeเดิม ไฟล์ไม่ได้ย้ายที่ แต่หลังrollbackจะกลับไปมีข้อจำกัดconflict/refreshแบบเดิม

อย่าสั่งmigrate:rollbackทั้งbatchเพราะมีmigrationsงานอื่นของผู้ใช้ และdownของmigrationนี้ปฏิเสธถ้ามีhistory หากต้องถอดschemaจริงต้องทำmaintenance/backuphistory/ตรวจไม่มีclientค้างและวางแผนเฉพาะ ไม่ลบdataหรือresetGitเพื่อrollback ไม่runcleanupphysicalfilesเพื่อแก้ปัญหาdeployment
